How database indexes work, why they make queries fast, and what they cost you. Use the arrow keys or the buttons below to move through the cards.

The problem

Without an index, the database reads everything

You ask for one customer by email. The database has no idea where that row lives, so it starts at row 1 and checks every row until it finds a match. This is called a full table scan.

SELECT * FROM customers WHERE email = 'sam@example.com';
0 rows checked
  • Work grows with the table. 10× more rows means roughly 10× more checking.
  • It keeps reading even after a match unless the column is known to be unique.
  • Fine for 50 rows. Painful for 50 million.
The idea

An index is the back of a textbook

You don't flip through all 600 pages to find "TCP handshake". You go to the index, which is sorted alphabetically, and jump straight to the page.

  • A database index is a separate, sorted copy of one or more columns.
  • Each entry stores the value plus a pointer to where the full row lives.
  • Because it's sorted, the database can jump right to the value instead of scanning.
Under the hood

Most indexes are B-trees

A B-tree is a balanced, sorted tree. At each node the database compares your value and picks one branch, throwing away everything else. Type a number and watch the path.

  • Root: "Is it less than 50?" One question eliminates half the data.
  • Middle: another comparison narrows it to a single leaf.
  • Leaf: holds the actual values and pointers to the table rows. 3 steps instead of 18.
The payoff

The bigger the table, the bigger the win

Where it helps

Four places indexes pay off

Any time the database needs to find, match, or order values in a column, an index on that column can help.

Filtering

Jump straight to matching rows.

WHERE email = 'sam@…'

Joining

Match rows across tables without scanning both.

JOIN orders o ON o.customer_id = c.id

Sorting

The index is already in order, so no sort step.

ORDER BY created_at DESC

Uniqueness

Primary keys and UNIQUE get an index automatically.

email TEXT UNIQUE
The trade-off

Indexes aren't free

Every index is another structure the database has to keep in sync. Reads get faster, writes get a little slower.

Faster readsSELECT, JOIN, ORDER BY
Slower writes + more diskINSERT, UPDATE, DELETE
  • Writes: insert a row and every index on that table also gets a new entry.
  • Storage: each index is a sorted copy of its columns, so it takes real disk space.
  • Worth it when a column is read often. Wasted when it's rarely queried.
Rules of thumb

What to index, what to skip

Don't index every column. Index the ones your queries actually lean on.

Index it

  • Columns in frequent WHERE clauses, like email or username
  • Foreign keys used in joins, like customer_id
  • Columns you sort or range-filter on, like dates
  • Large tables where scans are slow

Skip it

  • Tiny tables. A scan is already instant
  • Columns with very few distinct values, like a true/false flag
  • Columns you almost never search on
  • Write-heavy tables that are rarely read
Multi-column

Composite indexes read left to right

An index on (last_name, first_name) is sorted like a phone book: by last name first, then first name within each last name.

CREATE INDEX idx_name ON people(last_name, first_name);
WHERE last_name = 'Singh'

  • Skipping the first column is like searching a phone book by first name only.
Prove it

Ask the database with EXPLAIN

Put EXPLAIN in front of a query and the database tells you its plan. This is how you confirm an index is actually being used.

Before the index

EXPLAIN QUERY PLAN
SELECT * FROM customers
WHERE email = 'sam@example.com';

-- SCAN customers
Full table scan

After the index

CREATE INDEX idx_email
  ON customers(email);

-- SEARCH customers USING INDEX
--   idx_email (email=?)
Index lookup
  • The output above is SQLite style. Postgres and MySQL say things like Seq Scan vs Index Scan.
  • Look for the word SCAN on big tables. That's your hint an index might help.
